# PR Review: 029 US2: the tooth table and planned extractions

## Summary
The PR adds `tooth_loss.tooth_table`, one row per patient and tooth, and `tooth_loss.planned_extraction`, one row per
extraction ever on a plan. It also adds their base-R twin and parity on a seeded 200-patient sample, and writes both
tables to silver in the load job. The tests come first, and they cover:
- every status;
- a planned extraction later completed, which counts once;
- the spec's day-0/200/400 case (no exam after the loss is used);
- missing-at-entry teeth, which have only shared features;
- the spec's five-plan-copy case;
- the columns against the silver model;
- agreement with the hidden truth on a synthetic extract.

The full suite passes (1150 passed, 16 skipped). The spec 029 parity block was run locally in R 4.3.3 with 0
differences. Approve, with nits.

## Findings
### 🔴 Blocking (Critical)
None.
### 🟡 Should fix (Important, non-blocking)
- **Spark conversion of the derived tables is untested.** The load job hands pandas nullable `boolean` and `Int64`
  columns, and an object column with nulls (`last_mobility_code`), to `spark.createDataFrame`. If the first run fails
  on them, cast them in `save()`.
### 🟢 Nits / Suggestions
- **An exam on the extraction day counts as before the loss.** It is charted first, so this is the safer reading of
  "before". The module docstring says so. Revisit if real data shows exams charted after a same-day extraction.
- **A planned extraction with no diagnosis leaves the tooth `present` and unlabelled.** The spec lists no status for
  it. The docstring says so.
- **There are few perio labels at the default size** (2,000 patients: 33 extracted_perio and 85 planned_perio). The
  model PR (#371) should raise `n_patients` or the extraction rates, and report sample sizes with every metric.
